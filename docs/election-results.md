# Election results

The `#election` page displays Alaska and Mississippi's November 3, 2026 general-election Senate races. Alaska's counts are initial ranked-choice tallies. Only explicit AP winner flags receive winner labels.

Source: NPR's public 2026 election results JSON, tabulated by The Associated Press: https://apps.npr.org/2026-election-results/. State silhouettes also come from NPR's election assets. The page links to each state's original reporting.

Every page opening requests `GET /api/elections/2026/results?fresh=1`, bypassing the Worker result cache and requesting upstream revalidation. Previously cached totals stay hidden until that opening check succeeds; a failed opening check shows an error and Retry instead of displaying old totals. This includes returning to the tab immediately after leaving it. Opening checks add one source request per visit (concurrent checks in the same isolate share a fetch), with no extra D1 operations.

The browser reads live Senate results from the existing Rankings Worker at `GET /api/elections/2026/results` every 60 seconds while visible, and on focus/reconnection. The Worker fetches NPR's Senate JSON on demand and caches the two validated races for 120 seconds per Cloudflare location. There is no scheduled job, database write, new binding, or dependency on GitHub Pages builds. Concurrent requests within one Worker isolate share the same in-flight fetch. Cache expiry is fixed rather than extended by reads. NPR may itself cache or update its AP feed on a different cadence; an unchanged vote count can therefore be correct.

“Checked” shows when the Worker last retrieved and validated the source. Each race's “Updated” timestamp is NPR/AP's own timestamp. A failed refresh retains the browser's last loaded results with an error, and does not move the shared seen baseline. Failed or malformed upstream responses are never cached as fresh results. The old `data/election-results.json` and `scripts/update-election-results.mjs` remain a manual snapshot utility; the page no longer reads that file. Pages no longer has an election refresh cron or performs result retrieval during a build.

This adds 60 Worker requests per active viewer-hour, with zero D1 reads/writes for result retrieval. At one active cache location the source is fetched at most about 30 times/hour under steady traffic; more locations or cold starts can add source fetches. No traffic means no polling or source fetches. This is in addition to the existing baseline reads documented below, and uses ordinary small request-driven work rather than a background job. No migrations are needed. Deploy the Rankings Worker through the existing workflow with `apply_migrations=false`, then verify public results and Pages publication.

Each race lists the sum of all reported candidate votes (including Other), and a signed Democratic lead: the highest-voted Democratic candidate minus the highest-voted Republican candidate (D − R). A Republican advantage is negative; additional minor-party Republican/Democratic candidates are not summed into this lead. The top two named candidates are displayed individually; all remaining candidates and the source Other aggregate are combined into one Other row. Other vote changes compare the same current group against the saved raw baseline, including when a candidate moves into or out of the top two. Mark seen continues to save every raw candidate count, not the grouped display. The aggregate Other category contributes to totals but is not a candidate for the party lead. The previous signed lead is derived from the same candidates’ raw saved counts, so older baselines with an absolute `gap` remain correct without migration or marking seen again. The legacy stored `gap` is retained for compatibility and is not used by the signed display.

Admins can mark each race seen. The Rankings Worker stores one shared baseline per election year, state and race in D1 (`0019_election_seen.sql`). Public `GET /api/elections/2026/seen` returns all baselines, including for signed-out viewers. `PUT /api/elections/2026/seen/{state}/{raceId}` requires a signed manager token and the existing server-side Wyatt admin policy. Client-supplied admin flags and timestamps are not trusted. The Worker stamps the save time and derives totals and gaps from the submitted displayed candidate counts.

All users compare against the same server-saved timestamp and counts. Browsers check the shared baselines every minute and on focus; no browser-local baselines are imported or used. Conditional revisions reject competing admin tabs, and an older source cannot replace a newer baseline. Failed loads disable marking seen and display a warning; failed saves retain the prior shared baseline. Newly listed candidates are labeled new rather than assuming a previous zero count.

Rollout requires the Rankings Worker deployment and migration 0019 before the shared feature can work. Use the existing manual `deploy-rankings-worker.yml` workflow after explicit deployment approval and checking pending migrations. This change does not auto-deploy the Worker on a dev push.

The new table starts empty (no backfill or existing-row rewrite). A page load or minute refresh performs one public Worker request and one indexed query returning the two Senate race baselines. Each admin mark performs one conditional indexed insert/update affecting one row. Older baselines for other offices are not shown on this Senate-only page. Candidate JSON is bounded to 100 candidates per race. No extra scheduled jobs or scans of other tables are added. For 100 viewer-hours, the minute polling adds about 6,000 Worker requests and at most 12,000 result rows, before normal browser visibility throttling; actual use depends on visitors. Check account headroom if traffic materially increases. The baseline remains unset until an admin chooses Mark seen.
